# Multi-tenant follow-up reminder engine and customer/order state machines on PostgreSQL 18 + pg-boss (state as of 2026-11-09)

Verification method: library versions were read from the npm registry on 2026-11-09 (`https://registry.npmjs.org/<pkg>`); pg-boss behaviour was cross-checked against official docs (pgboss.io) AND by reading the published 12.38.1 package source (`dist/plans.js`, `dist/types.d.ts`); Temporal/Node were also run locally on Node v26.13.0. Items marked **[UNVERIFIED]** could not be confirmed from a primary source.

## 1. Scheduling approach: (a) pg-boss delayed jobs vs (b) next_due_at + sweeper vs (c) durable workflow engines

### Takeaway
For reminders that are cancelled/rescheduled often, the most robust option for a small team on Postgres is (b): an authoritative `followup_task` row with `due_at` (queryable, per-tenant-rule recomputable, cancel = one UPDATE), claimed by a sweeper with `FOR UPDATE SKIP LOCKED`, with pg-boss used as the executor/retry/dead-letter layer and cron trigger (a hybrid). pg-boss 12.38.1 does have everything needed for (a) too (delayed jobs, `singletonKey`, in-place `update()` by key, transactional send via Drizzle), but a delayed job is a poor system of record. Durable-workflow engines (c) are not justified at this scale; DBOS Transact is the only one that fits "Postgres-only, library not server", and it still adds a second durable-state model.

**(b) sweeper with SKIP LOCKED (PostgreSQL 18 docs)**
- "With `SKIP LOCKED`, any selected rows that cannot be immediately locked are skipped. Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table." ### Inferences
- **Why (b)+pg-boss hybrid wins for frequent cancel/reschedule:** the business rules ("earliest of appointment, quotation+3d, last interaction+3d", counter reset, max 2 resets, per-tenant numbers) are a *derived value* that must be recomputed on every inbound message. Storing it as one `next_due_at` column makes reschedule/cancel a single UPDATE in the same transaction as the state change, avoids orphaned delayed jobs, and answers manager questions ("what is due tomorrow for tenant X?") with SQL. Delayed pg-boss jobs hold the schedule inside the queue where it is awkward to query per customer and must be kept in sync with business rows by hand (cancel old + send new, or `update()` by key).
- pg-boss `short` policy + `singletonKey = customerId` + `update()`/`upsert()` by `singletonKey` is a viable "pure (a)" design that is genuinely idempotent (unique index guarantees a single pending job per customer); it is acceptable as an *acceleration* (precise firing instead of 30-s/60-s sweeper granularity) but the DB row must remain source of truth, and the job handler must re-validate the row (`due_at <= now() AND status='active' AND version matches`) before acting so stale jobs are harmless.
- Recommended executor split: sweeper = pg-boss cron (`schedule('followup-sweep', '* * * * *', null, { tz: 'Asia/Ho_Chi_Minh', missed: 'once' })`) or a self-looping job; the sweep does `UPDATE followup_task SET status='claimed', claimed_until=now()+interval '5 min' WHERE id IN (SELECT id FROM followup_task WHERE status='scheduled' AND due_at<=now() ORDER BY due_at LIMIT 200 FOR UPDATE SKIP LOCKED) RETURNING ...` and enqueues one pg-boss job per task in the same transaction via `fromDrizzle(tx, sql)`. pg-boss then gives retry/backoff, DLQ, dashboard, OTel. This reuses infra already deployed for webhooks and keeps one failure domain.
- Index: partial index `ON followup_task (due_at) WHERE status='scheduled'` (and `(tenant_id, due_at)` for per-tenant views) keeps the sweeper scan O(due rows) even at 100k active customers; PG 18 skip scan also makes `(tenant_id, due_at)` usable for queries without a tenant filter (inference from release-note feature).
- Durable engines add a second source of truth for the schedule, a version/determinism contract for long-lived workflows (a "5 follow-ups over weeks" workflow lives across deploys and per-tenant config edits), and ops/cost: Temporal needs its own cluster/visibility store or $50/M actions; Inngest/Trigger.dev/Hatchet cloud tiers have step/schedule caps or are external SaaS (data residency for VN tenants unclear); Restate server is BSL. For 5–30-person teams, ~100k customers, only DBOS fits "Postgres only, no extra server", but its value (multi-step compensation workflows) is not needed by reminders that are single-step with a state check. Revisit only if reminders become long multi-step orchestrations (e.g. AI-driven multi-channel sequences).
- Rate of scheduler load is low: 100k active customers with ~1 due event per customer per 3 days ≈ 0.4 due/s average; a Postgres sweeper with 1-min tick is far below any limit (back-of-envelope, not a benchmark).

## 2. State machines in TypeScript: XState v5 vs lightweight vs DB-enforced transition tables; audit log; concurrency control

### Takeaway
Keep the authoritative customer/order state in Postgres columns guarded by a **transition table + optimistic version check** (with an append-only history table), and use a plain TypeScript transition map (or a thin XState machine used only as a pure `transition()` function, not as a persisted actor) for validation/UI hints. XState v5 persistence exists but is explicitly fragile across machine-definition changes, and v6 is in beta with breaking snapshot/restore changes — a poor fit for long-lived, multi-tenant per-row state.

### Cited Findings
- XState latest stable is 5.33.4 (npm, published 2026-11-07); dist-tags also list `beta: 6.0.0-beta.1` and `alpha: 6.0.0-alpha.73` — [npm xstate](https://registry.npmjs.org/xstate); release page confirms 6.0.0-beta.0 (05 Nov) and beta.1 (06 Nov), "no further breaking changes planned for `@public` APIs" — [xstate releases](https://github.com/statelyai/xstate/releases).
- XState v5 persistence: `actor.getPersistedSnapshot()` returns JSON-serialisable state; restore with `createActor(logic, { snapshot })`; actions are not re-executed on restore, invocations restart; persistence is deep for children; "restored state may become incompatible if the machine or actor logic changes"; event sourcing is suggested when replaying actions matters; `machine.resolveState(...)` can rebuild from just state value + context — [Stately persistence docs](https://stately.ai/docs/persistence). The page does not cover delayed-event persistence or versioning of machine definitions (same source).
- XState v6 beta changes: restore moves to `restoreActor` from `xstate/persist`; `createActor` throws if given `snapshot`; snapshots are validated/migrated on restore; unrestorable snapshot yields an actor with an `'error'` snapshot; v5 config leftovers now throw; `@xstate/codemod` provides migration — [xstate releases](https://github.com/statelyai/xstate/releases).
- A GitHub-tracked issue reports restoring from a serialised persisted snapshot breaks history-state behaviour in v5 (status in current version not checked) — surfaced via [search result summary of Stately docs/issues](https://stately.ai/docs/persistence) **[UNVERIFIED, weak source]**.
- PostgreSQL READ COMMITTED: `UPDATE`/`SELECT FOR UPDATE` that hit a concurrently-updated row wait, then re-evaluate the `WHERE` clause against the new row version and apply to it; so `UPDATE ... WHERE id=$1 AND state='cho_coc'` is a safe compare-and-set — [PG 18 transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html).
- REPEATABLE READ: a concurrent committed update to a row you try to modify raises `ERROR: could not serialize access due to concurrent update` (SQLSTATE 40001) and the application must retry the whole transaction; SERIALIZABLE likewise requires retry on 40001; read-only transactions never conflict — [PG 18 transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html).
- Drizzle: `pgEnum` generates `CREATE TYPE ... AS ENUM`; `jsonb().$type<T>()` only affects TS inference, "won't check runtime values"; check constraints/generated columns are documented on separate pages — [Drizzle pg column types](https://orm.drizzle.team/docs/column-types/pg). drizzle-orm latest is 0.45.4 (2026-10-08) with `1.0.0-beta.*` tags in dist-tags — [npm drizzle-orm](https://registry.npmjs.org/drizzle-orm).
- PG 18 stores NOT NULL constraints in `pg_constraint` (nameable, NOT VALID) and adds `OLD`/`NEW` in `RETURNING` — [PG 18 release notes](https://www.postgresql.org/docs/18/release-18.html).

### Inferences
- **Pattern: transition table in DB.** `state_transition(entity_type, from_state, to_state, allowed_actor)` (or a composite FK from `customer_state_history(from_state,to_state)` to an allowed-pairs table) makes illegal transitions unrepresentable even if app code is buggy. Entities: `customer.state` as `text` + CHECK or enum; prefer **text + lookup table** over `pgEnum` because enum values cannot easily be removed/renamed and Vietnamese labels may evolve (use stable ASCII codes `moi, dang_tu_van, du_thong_tin, cho_coc, cho_xac_nhan_coc, da_coc, da_mua, tu_choi, khong_tiem_nang`; keep Vietnamese labels in an i18n map).
- **Write path (single statement CAS):** `UPDATE customer SET state=$to, state_version=state_version+1, state_changed_at=now() WHERE id=$id AND tenant_id=$t AND state=$from AND state_version=$expected RETURNING old.state, new.state` (PG 18 `old`/`new`), then in the same transaction `INSERT INTO customer_state_history(...)` and an outbox row. 0 rows updated => conflict (stale proposal/another actor); surface as 409. READ COMMITTED is sufficient because the compare-and-set predicate is re-evaluated after the wait; reserve SERIALIZABLE/REPEATABLE READ only for multi-row invariants (e.g. "customer cannot be `da_mua` unless an order is `hoan_tat`") and wrap those in a 40001 retry helper.
- **Validity check inside DB:** a `BEFORE UPDATE OF state` trigger that raises unless `(OLD.state, NEW.state)` exists in `state_transition` gives defense in depth (Drizzle has no native trigger DSL — ship as a custom SQL migration; **[inference, Drizzle trigger support not verified]**). Cross-entity rules (customer `cho_coc` while order `cho_coc`) belong in application service + tests, not triggers, to stay debuggable.
- **Order vs customer machines:** model the order machine as the master for deposit/delivery facts; derive customer states `Chờ cọc`, `Chờ xác nhận cọc`, `Đã cọc`, `Đã mua` from order transitions via the same transaction (an "effects" table: order transition X implies proposal/transition Y on customer). Terminal/side states (`Huỷ`, `Hoàn cọc`, `Đổi trả`) need explicit allowed-from sets; keep them as data in the transition table so changes ship as migrations with tests.
- **Audit/history:** append-only `*_state_history(id uuidv7, tenant_id, entity_id, from_state, to_state, actor_type ['human','ai','system'], actor_id, proposal_id, reason, evidence_quote, evidence_message_id, occurred_at timestamptz default now(), config_version)`; revoke UPDATE/DELETE on it from the app role. `evidence_quote` + `evidence_message_id` fulfil the "every AI-extracted fact carries its source sentence" principle. Optionally also keep it as the event source for the outbox (history row insert = event).
- **XState usage recommendation:** if wanted for developer ergonomics/visual docs, define the machine and call the pure `getNextSnapshot`/transition function against a snapshot rebuilt from `state` + `context` columns via `machine.resolveState` (documented in the persistence page) — never store opaque persisted-actor blobs; otherwise a 30-line typed transition map (`satisfies Record<CustomerState, readonly CustomerState[]>`) is enough. Given v6 beta moves restore APIs, depending only on the stable pure-transition surface limits migration cost. Pin `xstate@5.x`, do not adopt v6 beta in production yet.

## 3. "AI proposes, human confirms": proposals stored separately from authoritative state; expiry

### Takeaway
Store proposals in their own table (`state_proposal`) with evidence, base-state/version snapshot, status and expiry; authoritative state changes only through a human-confirm command that runs the same CAS transition as any other change and marks the proposal `accepted` in one transaction. Stale proposals are invalidated by the base-version check (state moved on) and by a TTL sweep.

### Cited Findings
- Product rules from project CLAUDE.md: AI proposes and humans decide; every AI extraction carries its source sentence; vague time expressions are asked back rather than inferred — [SalesMind CLAUDE.md](file:///d:/it/Project/SaleMindAI/CLAUDE.md) (local project file).
- pg-boss `short`/`stately`/`exclusive` queue policies with `singletonKey` can enforce "one pending job per key" in the DB — [pgboss.io/api/queues](https://pgboss.io/api/queues). Source for partial unique index approach (`WHERE state IN (...)`) used by pg-boss itself — [dist/plans.js](https://registry.npmjs.org/pg-boss/-/pg-boss-12.38.1.tgz).
- PG compare-and-set semantics under READ COMMITTED (see Section 2) — [PG 18 transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html).
- Postgres 18 temporal constraints (`WITHOUT OVERLAPS`) exist — [PG 18 release notes](https://www.postgresql.org/docs/18/release-18.html); usable for "at most one open proposal per (entity, kind) at a time" only via the simpler partial unique index below, since the overlap constraint targets ranges.

### Inferences
- Table sketch: `proposal(id uuidv7, tenant_id, entity_type, entity_id, kind ['state_transition','create_task','set_appointment','reschedule_followup'], payload jsonb, base_state text, base_version int, evidence jsonb [{message_id, quote}], model/prompt version, confidence, status ['pending','accepted','rejected','expired','superseded'], created_at, expires_at, decided_by, decided_at, decision_note)`.
- Unique partial index `ON proposal (tenant_id, entity_id, kind) WHERE status='pending'` => a new AI proposal for the same thing `superseded`-updates the old one (UPSERT in one tx) instead of piling up.
- **Accept flow:** `BEGIN; SELECT ... FROM proposal WHERE id=$1 AND status='pending' FOR UPDATE; apply CAS transition WHERE state=base_state AND state_version=base_version (or, softer, allow if transition from *current* state is still legal and show a diff); history insert with proposal_id; proposal -> accepted; outbox insert; COMMIT`. If CAS fails => mark `superseded`/`stale` and tell the human why.
- **Expiry:** two mechanisms: (1) lazy — reads filter `expires_at > now()` and accept refuses expired; (2) a pg-boss cron job (hourly) flips `pending` past `expires_at` to `expired` and emits an outbox event; also event-driven invalidation: any state/version change on the entity marks pending proposals with older `base_version` as `superseded` in the same transaction. TTL should be per-tenant/kind (e.g. 24–72 h for transitions; no TTL but re-ask for ambiguous dates).
- Ambiguous dates ("tuần sau", "đầu tháng") must produce a *question* proposal (`kind='clarify_date'`) with no date in payload rather than a guessed `due_at`; only a human-confirmed or customer-confirmed date may populate `appointment_at` (the "customer-confirmed appointment" rule).
- A Chờ-xác-nhận-cọc style state is itself a human-confirmation gate (deposit evidence); keep it as a normal order state, not a proposal, because it is a business state visible in reports.

### Gaps
- No external pattern source (blog/paper) specifically on human-in-the-loop proposal tables was retrieved; the design above is my synthesis, not a cited best practice.

## 4. Per-tenant configuration: JSONB vs typed columns, versioning, Drizzle support

### Takeaway
Use a small typed `tenant_followup_config_version` table (immutable, versioned rows, JSONB `settings` validated with Zod at write AND read) for the many tunable numbers, with a few typed columns for hot/queryable fields; stamp every follow-up task with `config_version_id` at creation so in-flight reminders keep consistent rules, and re-derive only on explicit events (reset, new info).

### Cited Findings
- Drizzle `jsonb().$type<T>()` provides only compile-time typing, not runtime validation — [Drizzle pg column types](https://orm.drizzle.team/docs/column-types/pg). Zod latest is 4.6.7 (2026-10-12) — [npm zod](https://registry.npmjs.org/zod). (Drizzle also ships a zod integration; not fetched **[UNVERIFIED]**.)
- Drizzle `timestamp({ mode: 'date' | 'string' })`; with `timestamptz` values are returned in the instance's configured time zone; string mode does no mapping — [Drizzle pg column types](https://orm.drizzle.team/docs/column-types/pg).
- PG 18: virtual generated columns are the default generated-column kind (computed on read), `STORED` still available — [PG 18 release notes](https://www.postgresql.org/docs/18/release-18.html).
- pg-boss `startAfter`, retry and queue settings are per-job/per-queue options and are copied at job creation (`Jobs inherit these unless overridden`) — [pgboss.io/api/queues](https://pgboss.io/api/queues); relevant analogy for "snapshot config at creation".

### Inferences
- **Hybrid storage:** typed columns for fields used in SQL predicates/joins (`tenant_id`, `version`, `effective_from`, `business_hours_profile_id`); JSONB for the rule parameters (`maxFollowups: 5`, `maxResets: 2`, `silenceGapDays: 3`, `quoteGapDays: 3`, `depositGapDays: 1`, `maxDepositReminders: 3`, `postSale: {photoAfterH, remainingPaymentRule, satisfactionAfterDays}`, `slaMode: 'calendar'|'business'`). Rationale: the rule set will grow (all numbers configurable) and per-field migrations per new knob are heavy; JSONB + Zod schema (with defaults and `schemaVersion` inside) keeps migrations additive.

Each `followup_task` stores `config_version_id` and its denormalised `attempt_no`, `reset_count`, `max_attempts_at_creation`. Policy: in-flight tasks finish under the version they were created with *unless* the tenant chooses "apply to open follow-ups" (then recompute `due_at` in a batch job and write a history row). This prevents surprising changes mid-sequence and gives an audit trail of which rule produced which reminder.
- Validate with Zod 4 at write (admin API) and at read (`parse` into a frozen config object, cache per `config_version_id` in-process since versions are immutable). Provide a code-defined default config merged under tenant overrides so new knobs have defaults without backfills.
- Also store `timezone` (default `Asia/Ho_Chi_Minh`) and a `holiday_calendar_id` per tenant (see Section 5).

## 6. Notifying salespeople in real time (brief): web push, SSE/WebSocket from Fastify, LISTEN/NOTIFY

### Takeaway
Use the outbox/`notification` table as truth, push to browsers via SSE (simple, one-way, works with Fastify) backed by Postgres LISTEN/NOTIFY (or pg-boss) to wake the API process, and add Web Push only for background/closed-tab alerts.

### Cited Findings
- `NOTIFY` payload must be < 8000 bytes (default); for larger data store a row and send its key; notifications are delivered only on commit and discarded on rollback; identical (channel, payload) notifications within one transaction are de-duplicated; transactions are delivered in commit order; a listener in a long transaction blocks queue cleanup; queue is 8 GB by default and NOTIFY fails at commit if full; the page does not discuss connection pooling — [PG 18 NOTIFY](https://www.postgresql.org/docs/18/sql-notify.html).
- pg-boss's own LISTEN/NOTIFY wake-up does not work via PgBouncer transaction/statement pooling modes — [pgboss.io/api/workers](https://pgboss.io/api/workers). Fastify latest is 5.12.8 (2026-11-02), `next` tag 6.0.0-alpha.6 — [npm fastify](https://registry.npmjs.org/fastify).

### Inferences
- LISTEN needs a dedicated, long-lived (non-pooled or session-pooled) connection per API process; send `NOTIFY tenant_events, '<tenant_id>:<notification_id>'` after commit (sent inside the same tx so it fires only on commit), fan out to SSE streams filtered by `tenant_id`/`user_id`, and let clients catch up via `Last-Event-ID` against the notification table (UUIDv7 ordering). Missed notifications while disconnected are recovered from the table, so NOTIFY loss is harmless.
- SSE vs WebSocket: reminders are server-to-client only, so SSE (HTTP/1.1 or h2, auto-reconnect) is the lighter choice; no source fetched comparing them for Fastify **[UNVERIFIED — no Fastify SSE plugin evaluated]**.

## 7. Transactional outbox on Postgres

### Takeaway
Write an `outbox` row (or a pg-boss job via `fromDrizzle(tx)`) in the same transaction as the state change; a relay delivers at-least-once; consumers must be idempotent. With pg-boss already in the stack, enqueueing the downstream job transactionally *is* the outbox, and a separate outbox table is needed mainly for events consumed outside pg-boss (SSE/notifications/analytics) or for an audit-grade event log.

### Cited Findings
- Pattern: store outgoing messages in an outbox in the same DB transaction as business data, a relay publishes them; guarantees messages sent iff the transaction commits, preserves order; relay may publish duplicates so consumers must be idempotent; two relay styles: polling publisher and transaction-log tailing — [microservices.io transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html).
- pg-boss + Drizzle: `boss.send(..., { db: fromDrizzle(tx, sql) })` inside `db.transaction` rolls back with the transaction — [pgboss.io/api/adapters](https://pgboss.io/api/adapters). pg-boss `transactional: true` workers commit handler writes together with job completion — [pgboss.io/api/workers](https://pgboss.io/api/workers).
- `SKIP LOCKED` is documented as suitable for queue-like tables with multiple consumers — [PG 18 SELECT](https://www.postgresql.org/docs/18/sql-select.html). NOTIFY is delivered only on commit — [PG 18 NOTIFY](https://www.postgresql.org/docs/18/sql-notify.html).
- Project rule: messages already ACKed to Meta must not be silently dropped — retry then dead-letter — [SalesMind CLAUDE.md](file:///d:/it/Project/SaleMindAI/CLAUDE.md).

### Inferences
- Use idempotency keys: `singletonKey = '<event_type>:<entity_id>:<version>'` on pg-boss sends (with `short`/`exclusive` policy or `singletonSeconds`) plus a `processed_event(consumer, event_id)` unique table inside the consumer transaction. Mind that `send()` returns `null` when deduplicated (not an error) — treat as success.
- Keep a thin `outbox(id uuidv7, tenant_id, aggregate_type, aggregate_id, event_type, payload, created_at, published_at)` table for non-pg-boss consumers; a pg-boss cron/looping job drains it with `FOR UPDATE SKIP LOCKED`, marks `published_at`, and prunes after N days.
- Caveat: pg-boss and your tables must be in the same database (same schema search path/connection) for the transactional send to be atomic — true in this project (single Postgres).

### Gaps
- No benchmark/recommendation fetched on logical-replication/CDC-based outbox (Debezium, `pg_logical_emit_message`) for Postgres 18; judged unnecessary at this scale but unverified.

## 8. Scale assumptions: tens–hundreds of tenants, ~100k active customers; is Postgres-only sufficient?

### Takeaway
Yes. The workload (sub-1 event/s average due reminders, sporadic bursts after Tet/holidays or after config recompute) is small for a single PostgreSQL 18 primary with a partial index on `due_at`; pg-boss and the sweeper share the same database. The main risks are burst fairness across tenants and table bloat from frequent updates, not raw throughput.

### Cited Findings
- pg-boss is designed as a Postgres-backed queue using `SKIP LOCKED`-style fetch, with per-group concurrency (`groupConcurrency`, enforced across nodes in DB), per-queue `partition: true`, retry/backoff, DLQ, dashboard, OTel — [pgboss.io](https://pgboss.io/), [queues](https://pgboss.io/api/queues), [workers](https://pgboss.io/api/workers), [OTel](https://pgboss.io/opentelemetry).
- 12.38.0 added batched maintenance and background migration changes (schema 46), indicating active work on large-table maintenance — [pg-boss releases](https://github.com/timgit/pg-boss/releases).
- PG 18: async I/O subsystem (`io_method`), skip scan, initdb enables data checksums by default; PG 18 supported until 2030-11-14 — [PG 18 release notes](https://www.postgresql.org/docs/18/release-18.html), [PG versioning](https://www.postgresql.org/support/versioning/).
- pg-boss docs mention alternative DB backends (CockroachDB, Citus, PGlite) — [pgboss.io](https://pgboss.io/) (not evaluated).
- Workflow-engine cloud costs scale per action/execution (Temporal from $50/M actions; Inngest Pro $99/mo incl. 1M executions; Hatchet $30/M runs after 1M; Trigger.dev $0.25/10k runs + compute) — vendor pricing pages cited in Section 1.

### Inferences
- Back-of-envelope: 100k active customers x ~1 reminder per 3 days ≈ 33k reminders/day ≈ 0.4/s average; even a 10x burst is trivial for Postgres. Each inbound message triggers one `due_at` UPDATE (hot rows) => keep `followup_task` narrow, use `fillfactor` ~80–90 so HOT updates apply, index only `due_at` (partial) to preserve HOT eligibility — **[general Postgres practice, not sourced in this session]**.
- Fairness: use `group: { id: tenantId }` + `groupConcurrency` in pg-boss workers so one tenant's bulk recompute/holiday-shift cannot starve others; in the sweeper, `ORDER BY due_at` with a per-tenant cap (e.g. window function `row_number() OVER (PARTITION BY tenant_id) <= N`) before locking.
- Operational guardrails: monitor sweeper lag (`now() - min(due_at) WHERE status='scheduled'`), dead-letter count, pg-boss `pgboss.queue.jobs` gauge; alert if lag > 5 min. Keep long-running transactions out of the workers (blocks vacuum) — general guidance.
- When to leave Postgres-only: multi-region/sharded tenants, >>1k jobs/s, or need for long multi-step orchestration with compensation (then evaluate DBOS first, Temporal Cloud second). None apply to the stated scale.

## 9. Recommended design (synthesis) and pitfalls checklist

### Takeaway
Postgres-native design: authoritative tables + `next_due_at` + sweeper claiming with SKIP LOCKED, pg-boss as executor (transactional send via `fromDrizzle`), transition tables + CAS for state machines, separate `proposal` table for AI suggestions, immutable versioned per-tenant config, Temporal API on Node 26 plus holiday data tables, outbox for events/notifications.

### Cited Findings
(All underlying facts are cited in Sections 1–8; this section lists design elements and links back.)
- pg-boss 12.38.1, Node >=22.12, PG >=13; `fromDrizzle`; `short` policy + `singletonKey`; cron with `tz` and `missed: 'once'`; `groupConcurrency` — [pgboss.io](https://pgboss.io/), [scheduling](https://pgboss.io/api/scheduling), [adapters](https://pgboss.io/api/adapters).
- Node 26 LTS with Temporal enabled by default; verified locally — [Node 26 release](https://nodejs.org/en/blog/release/v26.0.0), [previous releases](https://nodejs.org/en/about/previous-releases).
- PG 18.6 current; READ COMMITTED CAS semantic; SKIP LOCKED caveats; NOTIFY semantics — [PG versioning](https://www.postgresql.org/support/versioning/), [isolation](https://www.postgresql.org/docs/18/transaction-iso.html), [SELECT](https://www.postgresql.org/docs/18/sql-select.html), [NOTIFY](https://www.postgresql.org/docs/18/sql-notify.html).

### Inferences
**Core schema (sketch)**
- `followup_task(id uuidv7, tenant_id, customer_id, order_id null, kind ['silence','quotation','appointment','deposit','post_sale_photo','post_sale_balance','post_sale_csat'], status ['scheduled','claimed','done','cancelled','exhausted'], due_at timestamptz, attempt_no, reset_count, config_version_id, source_message_id, reason jsonb, claimed_until, version int)`. One *active* row per `(customer_id, kind)` via partial unique index `WHERE status IN ('scheduled','claimed')`.
- Rescheduling on customer reply = single transaction: cancel/replace row (`UPDATE ... SET due_at=..., attempt_no=0 or keep, reset_count=reset_count+1` guarded by `reset_count < max_resets`), write history row, outbox event. "Earliest of" rule = compute three candidate instants and take `LEAST()`; store which rule won in `reason` (explainability for the "evidence" principle).
- Reminder firing: sweeper claims rows; job handler re-reads row, checks `status='claimed'` and customer state still in an eligible set, then creates a **notification/task for the salesperson** (module is read-only; no messages to customers), increments `attempt_no`, and either sets next `due_at` (via rule) or `exhausted` + emits event. Claim leases (`claimed_until`) + the sweeper re-releasing expired claims protect against crashed workers; pg-boss retries/DLQ cover transient errors.
- State machines: `customer_state_transition` and `order_state_transition` tables + CAS write path + append-only history (Section 2); proposals in `proposal` table (Section 3); config versions (Section 4); calendars (Section 5); outbox + SSE (Sections 6–7).

**Pitfalls checklist**
1. Orphaned delayed jobs: never make a delayed job the only record of a reminder; handler must re-validate DB row (stale job = no-op).
2. `send()` returning `null` on dedupe/throttle is normal; do not treat as failure, but do not swallow genuine insert failures (project rule: no silent drops).
3. `deleteJob` can reopen throttle slots and break debounce — prefer `cancel`/status changes (pgboss.io/api/jobs).
4. pg-boss cron granularity is ~30 s check, one job/min/schedule, and occurrences are lost if no instance ran unless `missed: 'once'`.
5. `SKIP LOCKED` gives an inconsistent view: use only for claiming, never for counts/reports; with `ORDER BY ... FOR UPDATE` at READ COMMITTED rows can come back out of order (PG docs).
6. Never trust `jsonb().$type<T>()` for runtime safety — validate with Zod on read and write.
7. Do not persist XState actor snapshots as the source of truth; machine edits can invalidate stored snapshots; v6 beta changes restore API.
8. Time: never store local wall-clock strings; do not compute Tet from algorithms for scheduling; annual holiday data entry + per-tenant Tet block choice; warn when calendar data missing.
9. AI date extraction: ambiguous => question proposal, never a guessed `due_at`.
10. Config change mid-sequence: stamp `config_version_id` on each task; define explicit recompute policy.
11. Multi-tenant fairness: group concurrency + per-tenant caps in sweeper; always include `tenant_id` in every unique index and query (consider PostgreSQL RLS as defense in depth — **[not researched]**).
12. LISTEN/NOTIFY through PgBouncer transaction pooling breaks; use a direct/session connection for listeners.
13. pg-boss upgrades run schema migrations (schema 46 in 12.38.x) and the dashboard/proxy versions must be paired with the core version — [releases](https://github.com/timgit/pg-boss/releases).

- Items marked **[UNVERIFIED]** above; plus no hands-on prototype/benchmark was run in this session (only a local Temporal smoke test).
